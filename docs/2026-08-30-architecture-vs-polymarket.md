# 架构对比：预测大师 vs Polymarket（成熟市场参考）

> 日期：2026-08-30
> 背景：就"前端/公开暴露"议题调研 Polymarket 与成熟预测市场的落地方式，形成本项目架构对比与演进参考。

## 1. 为什么此对比重要

我们此前讨论过一个核心顾虑："前端起来 IP:8085 对外暴露，等于暴露给别人"。调研结论是——**成熟市场（Polymarket 为代表）的回答是：前端和链上本来就全公开，安全不靠藏**。公开市场数据是流动性的前提；真正受保护的是撮合引擎、API 密钥等**服务端能力**，与前端同源的合约地址、RPC、projectId 均非机密。

---

## 2. Polymarket 分层架构

```
┌───────────────────────────────────────────────┐
│  应用层：Web 前端（React/Next.js，CDN托管，公开）│
├───────────────────────────────────────────────┤
│  服务层                                        │
│  Gamma API（市场元数据，公开无鉴权）             │
│  CLOB API（订单簿/撮合，读公开 / 写 HMAC 鉴权）   │
│  Data API（持仓/P&L，按地址公开）                │
├───────────────────────────────────────────────┤
│  链上层：Polygon（结算层）                      │
│  Gnosis CTF（条件代币 ERC-1155）                │
│  UMA Optimistic Oracle（裁决）                 │
└───────────────────────────────────────────────┘
```

组成要素：

| 要素 | 说明 |
|------|------|
| 底部原语（不造轮子） | Gnosis Conditional Token Framework（条件代币）、UMA Optimistic Oracle（乐观预言机）、USDC 结算 |
| 撮合 | 链下中央订单簿（CLOB）+ operator 撮合引擎；撮合速度不受区块时间约束 |
| 结算 | 撮合结果批量提交 Polygon；订单为 EIP-712 签名消息，非托管 |
| 裁决 | UMA 乐观预言机：任何人支付保证金提案结果 → 2 小时挑战期 → 争议升级 UMA 代币投票 |
| 钱包 | "arcade/proxy wallet"（智能合约钱包）做上手体验与批处理 |
| 数据 | 索引器（subgraph / 自建 chain index）预聚合链上事件，前端经 API 读取 |

## 3. 逐项对比

### 3.1 架构总览

| 维度 | Polymarket | 预测大师（当前） | 说明 / 差距 |
|------|-----------|------------------|-------------|
| 链 | Polygon（137） | World Chain Sepolia（4801）→ 主网（480） | 目标链不同，理念一致 |
| 交易模型 | 限价单 + CLOB 链下撮合 | 链上 AMM/直接下单（每笔 bet 上链） | 我们的撮合更"链上原生" |
| 订单语义 | EIP-712 签名订单，授权撮合不托管资金 | `bet()` 链上交易（预授权 Approve） | 同属非托管；我们无订单簿 |
| 市场数据 | 索引器 + Gamma/CLOB API 预聚合 | 前端直连合约只读（view 调用） | 数据量小时直读够用 |
| 裁决 | UMA 乐观预言机（经济激励 + 争议挑战） | OracleAdapter + keeper `resolveMarket` | 我们为中心化 keeper 单点 |
| 治理/争议 | 平台中心裁量 + 附加上下文 | TokenHouse 代议制治理 + HumanHouse 争议投票 | 我们有链上原生治理，Polymarket 无原生治理 |
| 用户体验 | proxy wallet 批量 + 快速撮合 | 每操作单笔链上交易 | 我们链上延迟/手续费更高 |

### 3.2 "暴露"与安全模型对比

| 方面 | Polymarket | 预测大师 | 结论 |
|------|-----------|----------|------|
| 前端 / 市场数据 / 合约地址 | 全公开，靠 CDN | 全公开，Node 静态服务器 | 一致，无需担忧 |
| WalletConnect projectId | 内联进前端 | 构建时内联（.env → config.ts） | 一致，非机密 |
| 私钥 / 密钥 | 服务端（撮合签名、API 密钥），绝不进前端 | 仅部署仓库 `.env`（不入库），无服务端签名角色 | 一致 |
| 资金安全 | 合约结算 + 签名授权，非托管 | 合约结算，用户 Approve + bet | 一致 |
| 需要保护的"服务端能力" | 撮合引擎、HMAC 密钥 | 目前无（无客户端-服务端写路径） | 我们暂无此项负担 |

### 3.3 交易生命周期对比

```
Polymarket:
  签名订单(EIP-712) --POST--> CLOB operator --撮合--> 批量链上结算(CTF 转账) --> UMA 裁决 --> 赎回

预测大师:
  Approve(CoinToken) --> bet(marketId,outcome,amount) 上链 --> keeper resolveMarket(Oracle) --> claimReward
```

## 4. 成熟市场的共同规律（不限于 Polymarket）

1. **前端公开、链上可审计**：公开是常态，非缺陷。
2. **速度敏感部分下放链下**：撮合/行情放 operator 或索引器，链上只做结算、通证、裁决。
3. **复用成熟原语**：Gnosis CTF、UMA、proxy wallet——平台只写差异部分（撮合、体验、治理）。
4. **索引器 = 隐形后端**：前端不直接读链，经 API 层拿到预聚合数据（positions、P&L、candles、历史成交）。
5. **非托管贯穿**：订单/授权都是用户签名，operator 无权挪用资金。
6. 对照：**Kalshi** 走 CFTC 合规的中心化路线（撮合、托管、清算全中心化），是完全另一条路线，适合强监管市场；Polymarket + 我们的链上治理属于 crypto 原生路线。

## 5. 对本项目的启示 / 演进路线（按需，非必须）

当前规模下全链上撮合**可行且更链上原生**，以下均为"上量再动"的能力，不阻塞上线：

| 阶段 | 能力 | 触发条件 / 收益 |
|------|------|-----------------|
| P0（现状） | 前端 + 全链上撮合 + keeper 裁决 + 链上治理 | 已验证可用 |
| P1 | **索引器/API 层**：事件订阅 → 预聚合 positions/candles/历史 → 前端经 API 读 | 数据查询变慢、想减前端直读链 |
| P2 | **链下撮合**（CLOB） | 需要流动性做市 / 大额低滑点 / 高频 |
| P3 | **裁决去中心化**（乐观预言机/争议质押） | keeper 单点被质疑 / 上监管要求 |
| P4 | 域名 + nginx + HTTPS | 上线即做（见部署文档） |

## 6. 结论

- **本项目部署安全立场 = 最小暴露（Least Privilege）**：不必要不暴露，需要才暴露（公网只开业务口、安全组默认拒绝+白名单、链上权限与 Web 服务器分离）。Polymarket 的"全公开"是匹配其公开市场规模化需求；与本部署立场差异不影响架构对比结论。

- 我们的"暴露"顾虑在可比架构中**不成立**：公开是成熟市场标配，安全靠合约 + 服务端能力隔离，而非隐藏前端。
- 与 Polymarket 最大差异在三处：**撮合在链下（他们有）、裁决去中心化（他们有）、数据走索引器（他们有）**。三者都可按业务量级逐步补齐，先全部保持链上是最简单可靠的起点。
- 独有的优势：**TokenHouse + HumanHouse 链上治理/争议**是 Polymarket 没有的原生能力，可在合规叙事上做差异化。
